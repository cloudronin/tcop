# TCOP v0.4 deterministic confirmation-profile decisions

1. v0.4 is a parallel deterministic resolver profile. It consumes accepted
   immutable v0.2 observation, receipt, patrol, and relay records plus
   receiver-local v0.3 influence projections. It does not revise their wire
   formats, canonical bytes, validation rules, scenarios, artifact roots, or
   frozen regression digests.
2. Evidence class remains a receiver-validated classification derived from
   control-group identity. A valid signature establishes origin only; it does
   not itself grant corroborative credit or emergency authority.
3. A restricted or quarantined issuer can create an eligible investigative tip
   only from a fresh, validated, receipted threat observation. Its
   corroborative influence remains zero, and a tip never restores issuer
   reliability, counts as corroboration, or directly quarantines a subject.
4. Each receiver has a static direct-emergency registry. Direct-local emergency
   evidence MUST be a validated direct-local observation, name an authorized
   observation or enforcement point whose registered scope matches the
   observation, carry signed `direct_local_authorized` metadata, and carry a
   non-empty signed `independent_audit_ref`. The registry decision and audit
   reference are retained in local explanations and artifacts. A remote claim
   cannot use this path.
5. The default remote first campaign can create a scoped, reversible
   provisional constraint but cannot directly cause full quarantine. A
   provisional response has an explicit deadline and expiry. Time alone only
   de-escalates it to monitoring; it never escalates protection.
6. Confirmation requires a qualifying later event by default: authorized
   direct-local evidence, a failed independent patrol, or a fresh independent
   control group. Repeated observations, relays, and a later interaction from
   the original group do not satisfy source novelty in the default profile.
7. Events sharing a virtual time are processed from frozen pre-batch
   requirements and provisional states. New evidence can create a requirement
   in that batch but cannot satisfy its own requirement in the same batch.
8. Investigation scheduling is deterministic. It de-duplicates a tip key,
   applies a per-control-group cap and global budget, and allocates reserved
   capacity to high-risk scopes before low-risk work. Consequently a low-risk
   tip flood cannot consume the high-risk reservation.
9. A campaign is receiver-local and keys compatible evidence by subject,
   normalized scope, claim family, and a fixed virtual-time window. The
   lexicographically smallest compatible campaign ID is the canonical merge
   target; incompatible scope, claim, or timing creates a split with its
   deterministic predecessor; each compatible append creates an immutable
   revision. Relays retain original provenance and cannot create a new group
   or campaign credit.
10. v0.4 records four distinct measures: provisional-protection latency (first
    qualifying campaign to provisional enforcement), investigation latency
    (eligible tip to scheduled action), confirmation latency (requirement
    activation to accepted confirmation), and damage during the inclusive
    activation-to-deadline confirmation interval. They are not combined into a
    single response-time statistic.
11. Distributed TCX and faultable central comparison receive the same accepted
    observations, receipts, patrol outcomes, investigation facts,
    enforcement-adapter interface, and fault schedule. Their only intended
    difference is decision architecture.
12. All v0.4 output is isolated below `artifacts/confirmation-v0.4/`.
    `make research-confirmation` reruns upstream frozen-profile checks in
    temporary roots before writing its own suite and experiments.
